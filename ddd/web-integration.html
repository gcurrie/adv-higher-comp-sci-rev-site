Why This Page Exists

The DDD section of the question paper contains a question set in the context of a database-driven website, and part of it requires some integration with Web Design & Development. In practice that means DDD candidates must be able to design and read HTML forms — the front end that collects the data your SQL then stores or searches. It's typically worth around 2 marks, but they're marks you should never drop: the content is small and completely learnable.

Key Terms

action
FORM attribute naming the file (usually .php) executed when the form is submitted.
method
FORM attribute choosing how the data is sent — GET or POST.
GET
Appends the form data to the URL — visible, bookmarkable; for non-sensitive data.
POST
Sends the form data inside the request — hidden; for sensitive data and database updates.
name / value
Form data travels as name/value pairs — the name attribute is the key the server uses to read each value.
SELECT element
A drop-down list — its options define the values that can be submitted.
TEXTAREA
A multi-line text input.

The FORM Element — action & method

Every form needs two attributes that tell the browser what to do on submission:

HTML
<form action="registerStudent.php" method="POST">
    ...form elements...
    <input type="submit" value="Register">
</form>
  • action — the file that is opened/executed when the form is submitted. Because it's a .php file, the web server automatically executes the PHP code it contains — that code is what runs your SQL;
  • method — GET or POST, which determines how the data travels.

When the form is submitted, the browser builds a form data set of name/value pairs: each control's name attribute is the key, and the value is what the user entered (for text/number inputs) or what the HTML defined (for select and radio). The names must match the variables the server-side script expects — $_POST["firstname"] only works if an input was named firstname.

GET vs POST

Both methods start the same way — the browser constructs the form data set. Then they part company:

GETPOST
How data travelsAppended to the URL after a ?Encoded inside the message sent to the server
VisibilityVisible in the address bar and browser history — less secureHidden from the user — more secure
AdvantagesThe URL can be bookmarked and re-used; resent automatically after a connection issue; submissions can be cached (efficient for repeated queries)Handles non-ASCII characters; no length limit on the data; not stored in history
DisadvantagesASCII only; URL character limit restricts the data; stored in browsing historyCannot be bookmarked; browser asks the user to resubmit after a network issue
Use for…Non-sensitive data, e.g. the parameters of a database searchSensitive/personal data, and database updates
💡
Exam-ready rule of thumb: searching the database → GET is acceptable (bookmarkable, cacheable); inserting or updating personal data → POST (hidden, no length limit). Always justify with a property, not just the name.

Inputs, Select & Textarea

The form elements carried up from Higher — you should be able to read and write all of these:

HTML — the element toolkit
<!-- single-line text -->
<input type="text" name="firstname">

<!-- numeric input -->
<input type="number" name="tickets" min="1" max="6">

<!-- one choice from a group -->
<input type="radio" name="payment" value="card"> Card
<input type="radio" name="payment" value="cash"> Cash

<!-- drop-down list -->
<select name="play">
    <option value="Macbeth">Macbeth</option>
    <option value="Hamlet">Hamlet</option>
</select>

<!-- multi-line text -->
<textarea name="message"></textarea>

<!-- submit -->
<input type="submit" value="Book Tickets">

Note where each value comes from: the user types it for text, number and textarea; but for radio and select, the values are defined in the HTML code — the user just picks one. Query results sent back to the page are usually displayed in an HTML table built from <tr> rows of <th> (header) and <td> (data) cells.

Form Data Validation

Three kinds of validation are expected on form input — the same three you already know from database design, applied at the form:

  • Presence — the field must not be left empty (the required attribute);
  • Length — the entry must not exceed a maximum number of characters (maxlength);
  • Range — a numeric entry must fall between limits (min and max on a number input).

Spot the symmetry with the data dictionary: validating at the form catches errors before submission; the CHECK and NOT NULL constraints catch anything that slips through at the database. A well-designed system does both.

Test Yourself

Attempt each question first, then expand the marking instructions to check your answer.

GET or POST? — 2 marks

A website form asks new members for their name, address and date of birth, which are stored in a database table when the form is submitted.

State which method the form should use, justifying your answer with two properties of that method. (2 marks)

Marking Instructions
  • POST, because the submitted data is not visible in the URL/browser history — appropriate for personal data. (1 mark)
  • Any second property: no URL length limit on the data / non-ASCII characters can be submitted / POST is the standard method for database updates. (1 mark)
Reading a Form — 2 marks

A form contains:

<form action="findFilms.php" method="GET">
    <select name="genre">
        <option value="comedy">Comedy</option>
        <option value="horror">Horror</option>
    </select>
    <input type="submit" value="Search">
</form>

(a) State what happens when the Search button is clicked. (1 mark)
(b) State the name/value pair submitted if the user chooses Horror. (1 mark)

Marking Instructions
  • (a) The file findFilms.php is executed on the web server, with the form data appended to the URL (GET method). (1 mark)
  • (b) genre=horror — the name comes from the select element's name attribute, the value from the chosen option's value attribute. (1 mark)
