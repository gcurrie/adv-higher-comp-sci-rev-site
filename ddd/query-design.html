Why Design Queries?

At Advanced Higher, queries get complicated — grouped calculations filtered with HAVING, subqueries nested inside WHERE clauses. Planning the query in a design table first reduces the frustration of wrestling with SQL syntax, and in the exam, query design is assessed in its own right. The design of an SQL query should indicate:

  • the fields and/or calculations required;
  • the table(s) or query(-ies) that provide the details;
  • any search criteria to be applied;
  • what grouping is needed (if any);
  • the criteria applied to the grouping — the having row (if any);
  • the field(s) and direction used for the sort order.

All the examples on this page use the travel agency database (Resort, Hotel, Customer, Booking) from the Data Dictionaries page. The matching SQL for each design is on the SQL — DML page — design here, implement there.

Key Terms

Fields / Calculations
What the answer table will show — including computed values with their alias, e.g. Total Cost = SUM(…).
Search Criteria
Conditions applied to individual records — becomes the WHERE clause.
Grouping
The field(s) whose matching rows are summarised together — becomes GROUP BY.
Having
Conditions applied to the grouped results — becomes the HAVING clause.
Sort Order
Field(s) and direction (ascending/descending) — becomes ORDER BY.
Inner Query
A nested design block showing the fields, tables and criteria of a subquery whose result feeds the main query.

The Design Template

A simple table template captures everything. Leave rows blank when they're not needed — a blank row is information too (it says "no grouping in this query"):

Where do conditions go? If the condition tests individual records ("star rating over 3") it's search criteria. If it tests a summarised group ("resorts with at least two hotels" — a COUNT) it's having. This one decision is most of the marks in design questions.

Design Examples

Example 1 — HAVING with grouping and a row count

Display the resort name and number of hotels in any resort that has at least two hotels.

Field(s)/calculation(s)resortName, Number of Hotels = COUNT(*)
Table(s)/query(-ies)Resort, Hotel
Search criteria
GroupingresortName
HavingCOUNT(*) >= 2
Sort order

"At least two hotels" is a condition on a count of grouped rows — so it belongs in having, not search criteria.

Example 2 — HAVING with grouping and a sort

Display the full name and total cost of all bookings for each customer. Only list customers whose total cost exceeds £2000, biggest spender first.

Field(s)/calculation(s)firstName, surname, Total cost of all Bookings = SUM(pricePersonNight * numberNights * numberInParty)
Table(s)/query(-ies)Customer, Booking, Hotel
Search criteria
GroupingfirstName, surname
HavingSUM(pricePersonNight * numberNights * numberInParty) >= 2000
Sort orderSUM(pricePersonNight * numberNights * numberInParty) DESC

Three tables are needed because the price lives in Hotel, the nights and party size in Booking, and the name in Customer — the design must list every table the data touches.

Example 3 — logical operators in the search criteria

Display the surname, postcode and town of customers who live in towns beginning with the letters 'E' through to 'M', in alphabetical order of town.

Field(s)/calculation(s)surname, postcode, town
Table(s)/query(-ies)Customer
Search criteriatown BETWEEN "E" AND "M"
Grouping
Having
Sort ordertown ASC

The new logical operators (IN, NOT, BETWEEN, ANY, EXISTS) appear in designs exactly as they appear in SQL.

Designing Subqueries — the Inner Query Block

When a query needs a subquery, the design gains a nested inner-query block inside the search criteria row: the inner query gets its own fields/calculations, tables and search criteria, and the main query's criterion states how the inner result is used.

Example 4 — subquery in the WHERE clause

Display the hotel name, star rating and price per person for the most expensive hotel.

Field(s)/calculation(s)hotelName, starRating, pricePersonNight
Table(s)/query(-ies)Hotel
Search criteriapricePersonNight = [Inner query — Field(s): MAX(pricePersonNight); Table(s): Hotel; Search criteria: — ]
Grouping
Having
Sort order

Read it inside-out, the way the database executes it: the inner query finds the maximum price first, then the main query finds the hotel(s) whose price equals that value. You cannot do this in one flat query — WHERE pricePersonNight = MAX(pricePersonNight) is illegal, which is why the subquery exists.

Example 5 — subquery using NOT and IN

Display the names and types of resort not booked by the customer with ID 315.

Field(s)/calculation(s)resortName, resortType
Table(s)/query(-ies)Resort
Search criteriaresortName NOT IN [Inner query — Field(s): resortName; Table(s): Resort, Hotel, Booking; Search criteria: customerNo = 315 ]
Grouping
Having
Sort order

The inner query builds the list of resorts customer 315 did book; NOT IN then excludes them. Subqueries that return many rows must be used with multiple-value operators — IN, ANY or EXISTS.

Test Yourself

Attempt each question first, then expand the marking instructions to check your answer.

Complete the Design — 3 marks

Display the average price per person per night for each holiday resort. Only display resorts where that average exceeds £100.

Complete the design table for this query (fields/calculations, tables, grouping and having). (3 marks)

Marking Instructions
  • Field(s)/calculation(s): resortName, Average Price = AVG(pricePersonNight) (1 mark)
  • Table(s): Resort, Hotel; Grouping: resortName (1 mark)
  • Having: AVG(pricePersonNight) > 100 (1 mark)
Search Criteria or Having? — 2 marks

For each requirement below, state whether the condition belongs in the search criteria row or the having row of a query design, justifying each answer:

  • (a) "…only hotels with a star rating of 4 or more"
  • (b) "…only customers who have made more than three bookings"

(2 marks)

Marking Instructions
  • (a) Search criteria — it tests a value stored in each individual record (starRating >= 4). (1 mark)
  • (b) Having — "more than three bookings" is COUNT(*) > 3, an aggregate calculated on grouped rows, so it must be applied after grouping. (1 mark)
