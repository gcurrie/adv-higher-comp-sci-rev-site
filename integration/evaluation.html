Evaluation at Advanced Higher

At Higher you evaluated software against fitness for purpose, efficient use of coding constructs, usability, maintainability and robustness. All of those criteria survive at Advanced Higher — but they are reorganised, and one of them grows teeth. Every solution (SDD, DDD or WDD) is evaluated in terms of:

  • fitness for purpose
  • maintainability — now split into perfective, corrective and adaptive maintenance (this is the genuinely new content)
  • robustness

On top of that, each area keeps criteria of its own: efficiency and usability for SDD, accuracy of output for DDD, and usability for WDD. Evaluation is worth 5 marks of the project and up to 5 marks of the question paper.

Key Terms

Fitness for Purpose
The solution meets all of its functional requirements, as proven by testing.
Maintainability
How easily a solution can be changed after hand-over — supported by modularity, comments, meaningful names and white space.
Corrective Maintenance
Fixing errors found after release, so the solution adheres to its original specification.
Adaptive Maintenance
Changing the solution in response to changes in its environment — e.g. a new operating system.
Perfective Maintenance
Improving the solution — adding new features so it better meets user requirements.
Robustness
The solution copes with errors during execution without failing — it degrades gracefully rather than crashing.
Efficiency (SDD)
How well the code uses system resources — processor time, memory and storage — judged by the constructs chosen.
Accuracy of Output (DDD)
Queries return exactly the data asked for — the right rows, fields, groupings and calculated values.

Fitness for Purpose

A solution is fit for purpose if — following design, implementation and testing — it meets all the functional requirements identified during analysis. This is why analysis matters so much: the functional requirements written on day one become the checklist the finished product is judged against.

The evidence comes from final testing. While creating your test data you calculated expected results; if the actual output matches the expected output for every functional requirement, the solution is fit for purpose.

Example — an evaluation that concludes "not fit for purpose"

A database-driven shop website successfully implements all its insertions, deletions and edits — but it does not display confirmation of those actions, and it does not let the customer sort search results. Both were functional requirements (outputs and processes) in the requirements specification, so despite everything else working, the evaluation must conclude the solution is not fit for purpose — and state exactly which requirements were not met.

💡
In your project evaluation, walk through the functional requirements one by one and state whether each was met, citing test results. An honest "requirement 6 was not met because…" earns marks; a vague "my project works well" does not.

Maintainability — the Three Types of Maintenance

Maintenance is the process of changing a solution after it has been written and handed over. At Higher, "maintainability" meant writing code that is easy to change: modular structure, meaningful variable and module names, effective internal commentary and white space/indentation. All of that still supports maintainability at Advanced Higher — but now you must also be able to name and distinguish the three types of maintenance a solution may need:

TypeWhat it isTriggerExample
Corrective Fixing bugs that made it through testing, so the solution adheres to its original specification. An error is discovered after release. A leap-year date bug in a booking system is patched.
Adaptive Amending the solution in response to changes in its operating environment — the requirements haven't changed, the world has. New OS, new hardware, new database version, changed law. A program is updated so it runs after the organisation moves from Windows 10 to Windows 11.
Perfective Improving the solution — adding new features so it better meets user requirements. Users request functionality beyond the original specification. An export-to-PDF feature is added to a reporting tool.
⚠️
Common exam confusion: corrective vs perfective. Ask: was the behaviour wrong against the original specification? If yes, fixing it is corrective. If the solution worked as specified but users now want more, that's perfective. If nothing about the requirements changed but the environment did, it's adaptive.

Robustness

Robustness is the solution's ability to cope with errors during execution without failing. A robust program does not crash out when it meets unexpected input or an external error (a missing file, a lost database connection) — it gracefully handles the error: it notifies the user and provides a point from which they can continue.

Two things worth stating in an evaluation:

  • Robustness is judged from the results of testing with exceptional data and destructive testing — trying to break the solution;
  • A solution can meet every functional requirement (be fit for purpose) and still not be robust — the two criteria are independent.
Example — robustness in an integrated solution

A program that reads from a database should not crash if the connection fails. Placing the connection code inside a try structure so the program reports "could not connect to the database" and returns to the menu is a robustness feature — worth describing explicitly in a project evaluation.

Area-Specific Criteria

The remaining Higher criteria did not disappear — they were assigned to the area where they make sense:

SDD — Efficiency

Efficiency relates to how the software uses system resources: processor time, memory and storage. At this level it is assessed by reviewing the efficiency of the code:

  • Reuse of modular code — one parameterised validation function called three times beats three near-identical loops (see the worked comparison on the OOP page);
  • Choice of data structure — a 2D array or array of records instead of a jumble of separate variables; a linked list when frequent insertion/deletion is needed;
  • Choice of algorithm — a binary search on sorted data makes far fewer comparisons than a linear search; an insertion sort usually beats a bubble sort. The efficiency arguments are covered in detail on the Standard Algorithms page.

SDD — Usability

Usability is the extent to which specified users can achieve specified goals with effectiveness, efficiency and satisfaction. A usable interface is:

  • easy to learn from first use;
  • simple to use to achieve the program's purpose — it guides the user through the task;
  • memorable — once used, the user can recall how it works on future visits.

Evidence comes from usability testing on prototypes and end-user testing.

DDD — Accuracy of Output

Accuracy of output asks: do the queries return exactly the data asked for? The right rows, the right fields, correct calculated values, correct grouping — compared against expected answer tables prepared before testing. A query that returns the right customers but includes duplicates, or rounds a calculation wrongly, fails this criterion even though it "runs".

Test Yourself

Attempt each question first, then expand the marking instructions to check your answer.

Types of Maintenance — 3 marks

State the type of maintenance being carried out in each of the following, justifying each answer:

  • (a) A supermarket's stock program is amended after the company replaces its Windows tills with Android tablets.
  • (b) A payroll program occasionally calculates overtime incorrectly; the calculation is fixed.
  • (c) Users of a homework app ask for — and receive — a new dark mode.

(3 marks)

Marking Instructions
  • (a) Adaptive — the program is changed in response to a change in its operating environment (new platform). (1 mark)
  • (b) Corrective — an error is fixed so the program adheres to its original specification. (1 mark)
  • (c) Perfective — a new feature is added to better meet user requirements. (1 mark)
Fitness for Purpose vs Robustness — 2 marks

A finished program meets every functional requirement in its specification, but crashes when the user types a letter instead of a number.

Evaluate this program in terms of fitness for purpose and robustness. (2 marks)

Marking Instructions
  • The program is fit for purpose — testing shows it meets all the functional requirements identified at analysis. (1 mark)
  • The program is not robust — it fails to cope with unexpected input during execution (it crashes rather than handling the error gracefully). (1 mark)
SDD Efficiency — 2 marks

A program searches a sorted array of 10 000 customer records using a linear search. Describe one change that would improve the efficiency of this program, and justify your answer. (2 marks)

Marking Instructions
  • Replace the linear search with a binary search. (1 mark)
  • The data is already sorted, and a binary search halves the search area with each comparison — at most 14 comparisons for 10 000 items, against up to 10 000 for a linear search. (1 mark)
