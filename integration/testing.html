Testing at Advanced Higher

At Higher, testing meant a comprehensive final test plan with normal, extreme and exceptional data, plus debugging techniques. All of that still applies — but Advanced Higher names five distinct stages of testing and expects you to know when each happens, who carries it out and why. The order matters: testing moves outwards, from individual modules, to connected components, to the whole solution, to real users.

Testing is worth 15 marks of the project and between 2 and 8 marks of the question paper.

Key Terms

Component Testing
Testing individual modules (functions, procedures, queries) as they are developed. SDD-specific in the course spec.
Integrative Testing
Testing that independently developed components work correctly when connected to each other — verifies the interfaces between them.
Usability Testing
Testing based on prototypes, using personas, test cases and scenarios, to find interface problems early.
Persona
A fictional but realistic profile of a target user, used to focus usability testing on real user needs.
Final Testing
Testing the finished solution against the functional requirements before hand-over.
End-User Testing
Representative end users test the finished solution to confirm it meets their needs.
Temporary Code
Extra code added purely to prove an integrative test worked (e.g. displaying a "connection successful" message), removed once the test passes.
ℹ️
The order of the stages: component testing happens during development → integrative testing happens once separate components are connected → usability testing happens on prototypes (so it can start early) → final testing and end-user testing happen on the finished solution.

Component Testing (SDD)

Component testing takes place during the development of the solution, as individual functions or modules are created. Each module is tested on its own, before it is connected to anything else, so that errors are found while they are still cheap to fix.

Because a module under test may depend on other modules that don't exist yet, programmers use:

  • a stub — a dummy function or procedure that stands in for a module that has not been written yet (it might simply return a fixed value);
  • a driver — code written purely to call the module being tested with known test data and display the result.
Example — component testing a validation function

A program includes a function validate_input(min, max). Before the rest of the program exists, the developer writes a short driver that calls the function with normal (15), extreme (10, 20) and exceptional (9, 21, "ten") values and checks the function only returns values in range. The function is proven correct in isolation before it is used anywhere.

All your Higher debugging techniques — dry runs, trace tables, breakpoints and watchpoints — are the tools used to find errors during component testing.

Integrative Testing

Integrative testing is the second level of testing, and it takes place after component testing. It is needed whenever a project connects separately developed components — which every Advanced Higher project does, because your project must integrate two technologies. Its purpose is to verify the interaction between components and to detect interface defects: do independently developed units of software work correctly when connected to each other?

Temporary code

This is the detail examiners love. Some integrative test cases require temporary code — code that generates results not mentioned anywhere in the requirements specification, added purely to prove that a connection or transfer worked. Once the test passes, the temporary code is removed.

Example — integrative tests for a diary app (SDD + DDD)

A personal diary program stores its entries in a database. Three integrative tests (* = requires temporary code):

Test case objectiveDescriptionExpected result
Check communication from the program to the database server*Use program code to connect to the database serverA message is displayed confirming a successful connection
Check all diary entries are selected from the database and stored in the array of records*Execute the SQL query, store the results in the array of records, then display the array's contentsAll diary entries in the database are stored in the array and displayed successfully
Check a new diary entry has been added to the databaseEnter a new entry and execute the SQL INSERTA new record appears in the database table (check the table's contents)

The "connection successful" message and the code that dumps the whole array to the screen are temporary code — neither appears in the functional requirements, and both are deleted once the tests pass.

💡
In your project, integrative testing is where you prove the two technologies actually talk to each other: program ↔ database, web page ↔ database, form ↔ PHP. Plan at least one integrative test per integration functional requirement — and say explicitly which tests used temporary code and that it was removed.

Usability Testing Based on Prototypes

Usability testing does not wait for the finished product. It is carried out on prototypes — early versions or even paper mock-ups of the interface — so that layout and navigation problems are found before they are expensive to fix. The results of testing one prototype feed into the next.

Usability testing is structured around three things:

  • Personas — fictional but realistic profiles of target users (name, age, experience, goals, frustrations). Testing "as" a persona keeps the focus on real users rather than on the developer's own habits;
  • Test cases — specific tasks the tester attempts ("add a new diary entry", "find last Tuesday's entry"), each with an expected outcome;
  • Scenarios — the realistic context wrapped around a test case ("you are a first-time user who wants to…").
⚠️
Personas are examinable — and required in your project. Persona-based usability testing is listed at Higher level under Web Design & Development, but it applies to every Advanced Higher project regardless of which technologies you integrate. Write one or two short personas during analysis and test your prototypes against them.
Example — a persona

Morag, 67, retired teacher. Uses a tablet daily for email and news but has never used a booking app. Wants to book a fitness class in under two minutes without creating an account. Frustrated by small text and jargon.

A test case for Morag: "Book a Tuesday yoga class" — expected outcome: completed within two minutes with no assistance. If Morag's persona can't complete it, the prototype's navigation needs revised before implementation.

Final Testing

Final testing is carried out on the finished solution, before it is handed over. It is the Advanced Higher version of the comprehensive testing you did at Higher: the complete solution is tested against every functional requirement in the requirements specification, using a planned test table of normal, extreme and exceptional data with expected and actual results.

The results of final testing are the evidence you cite when evaluating fitness for purpose — if every functional requirement passes its tests, the solution is fit for purpose.

End-User Testing

End-user testing puts the finished solution in front of representative end users — people who match the intended audience, not the developer. They attempt realistic tasks and report whether the solution meets their needs. Where usability testing on prototypes found design problems early, end-user testing confirms (or denies) that the finished product actually works for its audience.

ℹ️
Don't confuse the two "user" tests: usability testing happens on prototypes, early, using personas and scenarios; end-user testing happens on the finished solution, at the end, using real representative users.

Area-Specific Testing

On top of the five stages, the course spec adds tests specific to each optional area:

AreaTestWhat it means
SDDComponent testing during developmentAs described above — each module tested as it is written.
DDDSQL-implemented tables match designCompare every CREATE TABLE against the data dictionary: field names, data types, sizes, keys and validation must all match. A field created as varchar(20) when the dictionary says varchar(40) is a failed test.
SQL operations work correctlyRun each query against data with a known expected answer table, and compare actual output against expected output — including checking that searches, sorts, groupings and calculations return exactly the right rows.
💡
A classic DDD exam task: you're shown an SQL statement and its incorrect output alongside the expected output, and asked to identify how to correct the statement. Practise this on the SQL Practice Questions page.

Test Yourself

Attempt each question first, then expand the marking instructions to check your answer.

Integrative Testing & Temporary Code — 2 marks

A student's project is a recipe manager program that stores recipes in a database. One of their test cases is: "Use program code to connect to the database server — expected result: a message is displayed confirming a successful connection."

(a) State the type of testing being carried out. (1 mark)
(b) Explain why the code that displays the confirmation message should not appear in the finished program. (1 mark)

Marking Instructions
  • (a) Integrative testing — it verifies the interaction between the program and the database components. (1 mark)
  • (b) It is temporary code — the confirmation message is not part of the functional requirements; it exists only to prove the test, so it is removed once the test is successful. (1 mark)
Ordering the Stages — 2 marks

A development team carries out the following tests on a database-driven website:

  • A — representative customers use the finished website to place orders
  • B — each PHP function is tested with a driver as it is written
  • C — a paper prototype of the checkout page is tested against a persona
  • D — the form submission is checked to confirm data reaches the database

Name the type of testing used in each of B and D. (2 marks)

Marking Instructions
  • B — component testing: an individual module is tested during development. (1 mark)
  • D — integrative testing: it verifies that two separately developed components (form and database) work when connected. (1 mark)

(For reference: A is end-user testing; C is usability testing based on a prototype.)

DDD Testing — 1 mark

A candidate has implemented their database using SQL CREATE TABLE statements. Describe one test they should carry out on the implemented tables before entering any data. (1 mark)

Marking Instructions

Check that the implemented tables match the design — compare the tables against the data dictionary to confirm field names, data types, sizes, primary/foreign keys and validation are all as designed. (1 mark)
